# PowerPoint vs pptxgenjs: differences to accept, not fix

The structural comparison reports every difference it finds between two decks. When the two decks come
from different engines — a reference authored in PowerPoint against a deck generated by pptxgenjs —
some of those differences are artefacts of the engine pair rather than drift in the generator. They
cannot be removed by writing the generator differently, and chasing them wastes a build cycle each time.

Four such differences are known. Check a discrepancy against this list before treating it as a defect.

## 1. Run coalescing on save

**What you see.** A paragraph whose text matches exactly, but whose run count differs — one run on the
PowerPoint side against several on the generated side.

**Why.** PowerPoint coalesces adjacent runs carrying identical character formatting when it saves the
file: three consecutive fragments in the same font, size and colour come back as one `<a:r>`. pptxgenjs
does no such merging — it emits one run per `addText` fragment, so a call built from an array of text
objects produces exactly that many runs even when they are formatted identically.

**What to do.** Compare the concatenated paragraph text and the formatting of the runs, not the run
count. `compare_decks.py` follows this rule: it flags a run-count mismatch, but marks it as a probable
engine artefact whenever the paragraph text itself matches.

## 2. Straight arrow: connector vs line autoshape

**What you see.** The same visible arrow reported with a different shape kind or geometry on each side.

**Why.** In PowerPoint a straight arrow drawn between two shapes is a **connector** — a `<p:cxnSp>`
element with `prstGeom prst="straightConnector1"`. pptxgenjs has no connector primitive; `addShape` with
the `line` type emits an ordinary autoshape, a `<p:sp>` with `prstGeom prst="line"`. The two elements
are different at the XML level but carry the same offset, extent and line properties, so they fold to
one visible form: identical position, identical length, identical stroke and arrowhead.

**What to do.** Treat a `cxnSp`/`sp` and a `straightConnector1`/`line` pairing as equivalent when the
frame and line properties match. A difference in the frame or the stroke is real; the element name
alone is not.

## 3. Table height: requested vs computed

**What you see.** A table whose height differs between the decks, often by a noticeable amount, while
every row and every cell matches.

**Why.** The height pptxgenjs writes is the height that was *requested* in the generating call. The
height PowerPoint writes is the one *computed* after it has laid out the rows — a row grows to fit its
wrapped text, and the table's stated height follows. The two agree only when the requested height
happened to match what the layout needed.

**What to do.** Ignore the table's own height. Compare the column widths, the row count, the cell text
and the cell formatting instead; those are authored values on both sides. This is why the coordinate
tolerance is a flag: no single value makes a table height comparable, so exclude it from what you read
rather than widening the tolerance for the whole deck.

## 4. Line style: inherited from the theme vs written out

**What you see.** A shape whose outline is reported as unset on the PowerPoint side and fully specified
on the generated side — or the same discrepancy for a colour that is a theme reference in one deck and
a literal hex in the other.

**Why.** A shape edited in PowerPoint relies on **inheritance**: it carries a style reference into the
theme (`<p:style>` with `lnRef`, `fillRef`, `effectRef`) and leaves the concrete properties out of the
shape, so the theme's line style applies. pptxgenjs writes the properties **explicitly** on the shape —
the resolved width, colour and dash pattern — and does not lean on the theme. Both render identically
as long as the explicit values match what the theme resolves to.

**What to do.** Resolve the theme value once by hand (`dump_slide.py` on the reference shows what the
shape itself declares; what it does *not* declare is inherited), confirm the generated deck writes that
same value, and then treat the "unset vs set" pairing as expected. A generated value that differs from
the resolved theme value is a real difference.
